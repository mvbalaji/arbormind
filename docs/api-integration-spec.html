Arbormind CRM — Configurable API Integration Layer

A complete requirements specification and implementation blueprint for a metadata-driven, multi-partner enterprise integration platform. Prepared for CIO/CTO review.

Version 2.0.0 Status Draft — CTO Review Classification Internal · Restricted Owner Platform Engineering Date July 2026 Target Q4 2026 GA
Executive Summary

Strategic Context & Objectives

The Arbormind CRM currently operates as a standalone system. To fulfil its role as the system of record for customer relationships, it must exchange data reliably with ERP, billing, identity, case management, and marketing platforms. Ad-hoc, point-to-point integrations are expensive to build, fragile to operate, and impossible to audit. This specification defines a configurable, metadata-driven Integration Layer that replaces all point-to-point connections with a single, governed middleware platform.

The Integration Layer is configured entirely through an admin UI — no new deployment is required to add a field mapping, onboard a new partner, or change a transformation rule. Every configuration change is versioned, audited, and promotable across environments. Authentication credentials are stored in a secrets vault and never appear in the configuration database or application logs.

2.3 Error Handling, Retries & Idempotency

Idempotency Key Strategy

Every outbound mutating request (POST, PUT, PATCH, DELETE) carries an X-Idempotency-Key header. The key is derived as sha256(tenantId + entityType + entityId + operationType + timestampBucket) where timestampBucket is truncated to the nearest 5-minute window. Partners that support idempotency keys honour them server-side. For partners that do not, the Integration Layer performs a pre-flight lookup to avoid duplicate creation.

Retry Policy

ConditionActionMax RetriesBack-off
HTTP 429 (rate limited)Retry after Retry-After header value (or 5 s default)5Honour partner-specified delay
HTTP 500, 502, 503, 504Exponential back-off with jitter5Initial 500 ms, multiplier 2×, jitter ±20%, cap 32 s
Network timeout / connection refusedExponential back-off3Initial 1 s, multiplier 2×, cap 8 s
HTTP 400, 401, 403, 404, 409, 422No retry — log to error queue for manual review0N/A
Authentication 401 (token expired)Token refresh once, then retry original request once1 (after refresh)Immediate

Dead-Letter Queue (DLQ)

Any record that exhausts retries is moved to a per-partner DLQ topic in Kafka. DLQ entries carry the original payload, all retry attempts with timestamps and HTTP responses, the final error classification, and the mapping template version used. The Ops dashboard surfaces DLQ depth with per-partner breakdown. Operators may requeue (replay), requeue with patch (modify payload before replay), or discard (with mandatory reason code) individual DLQ entries.

Circuit Breaker

StateCondition to EnterBehaviourExit Condition
Closed (healthy)DefaultAll requests pass through normally—
Open (tripped)5 failures in 30 s window OR error rate > 50% over 60 sRequests immediately rejected with 503; no outbound call made. Alert fired.After 60 s cooldown, one probe attempt
Half-openAfter cooldownSingle probe request forwarded. If success → Closed. If fail → Open (reset 60 s timer).Probe success

Circuit-breaker state is tracked per-partner and persisted in Redis so all orchestrator pods share the same view. State transitions are audit-logged.

2.4 Multi-Tenancy Architecture

The Integration Layer is designed for logical multi-tenancy with physical isolation of secrets and audit data. All configuration records carry a tenant_id column enforced at the ORM layer (Drizzle row-level filter applied automatically). API gateway resolves tenant from subdomain ({tenant}.api.crm.io) or JWT tid claim. Partner credentials are scoped per-tenant and never shared across tenant boundaries.

Architectural Decision Required
Initial release targets single-tenant deployment (one DB schema per customer). Full logical multi-tenancy (shared schema, RLS) is architected but gated behind a feature flag. Recommend deciding before schema freeze in Sprint 4.

Configurable Field Mapping Framework

The mapping framework is the architectural core of the Integration Layer. Field mappings, transformation rules, and validation logic are stored as structured metadata in a versioned configuration database. The Mapping Engine reads this metadata at runtime — no code change or deployment is required to alter a mapping, add a transformation, or onboard a new field.

Design Principle
Validation is fail-collect, not fail-fast. All validation errors for a record are gathered before rejection, so the error log shows the complete list of issues — not just the first one encountered. This eliminates iterative fix cycles.

3.4 Mapping Templates

Each integration partner has one Mapping Template Set — a named, versioned collection of entity templates. Templates may be:

  • Cloned from a library of base templates (e.g. "SAP S/4HANA Default", "Stripe Default") and then customised.
  • Exported / imported as JSON for version control in Git alongside code.
  • Promoted independently per environment (DEV → QA → PROD) with a mandatory reviewer sign-off in QA and PROD.
  • Rolled back to any prior version in one click from the admin UI. Rollback is itself an audited event.

When a new template version is saved, the prior version is immutably archived. A version can be marked deprecated (still functional, ops alerted) or locked (read-only, cannot be promoted).

3.5 UI-Driven Mapping Configuration

Non-engineering users (Integration Admins, Business Analysts) configure mappings through the CRM admin panel. The UI presents:

  • A source schema browser — a tree view of all CRM entity fields, auto-populated from the CRM OpenAPI spec.
  • A target schema browser — imported from the partner's OpenAPI or JSON Schema spec (uploaded by Integration Admin).
  • A drag-and-drop mapper — draw lines from source fields to target fields; transformation rule picker appears inline.
  • A test runner — paste a sample CRM record; run the mapping; see the transformed output and any validation errors before saving.
  • A diff view — side-by-side comparison between the current version and any prior version.

4.4 Custom Fields & Dynamic Schema Extension

CRM admins may define custom fields on any entity. The Integration Layer supports custom fields through a dynamic schema registry: when a custom field is added to a CRM entity, it immediately appears in the source schema browser and can be mapped without any code change. Custom field metadata (name, data type, entity, validation) is fetched from the CRM API by the Integration Layer admin UI on demand.

Configuration Management Requirements

5.1 Versioning Model

Every save of a mapping template creates an immutable version record. The version model follows semantic versioning conventions adapted for configuration:

Version SegmentIncremented WhenExample
MajorBreaking change: a field removed or renamed in a way that would cause partner rejection. Requires explicit acknowledgement.3.0.0
MinorNew field mapping added, new transformation rule added, validation rule relaxed.2.1.0
PatchCorrection to an existing rule (e.g. regex fix, default value change) that does not alter the set of mapped fields.2.0.1

Each version record stores: author user ID, timestamp, version number, change description, full serialised mapping JSON, diff from prior version (unified diff format), and promotion history per environment.

5.2 Environment Promotion Workflow

1

Draft (DEV)

Integration Developer creates or edits a mapping template. Test runs against DEV partner sandbox. No approval required. Draft versions cannot be promoted directly to PROD.

2

QA Promotion

Developer requests promotion to QA. Integration Admin reviews the diff and approves or rejects with comments. On approval: template deployed to QA environment; automated contract tests run against QA partner sandbox.

3

PROD Promotion

After QA sign-off, Integration Admin requests PROD promotion. A second approver (Senior Integration Admin or Engineering Lead) must approve. Promotion is scheduled to a change window. Rollback to prior PROD version available for 30 minutes post-promotion.

4

Rollback

Any prior approved version can be re-promoted to PROD by an Integration Admin. Rollback is an audited event. Post-rollback, a blameless incident review is required within 48 hours.

6.2 Orchestration Service — Detailed Design

The Orchestration Service is a stateless Node.js (TypeScript) microservice deployed as a Kubernetes Deployment with HPA (Horizontal Pod Autoscaler) keyed on Kafka consumer lag and CPU utilisation. It is the only service that makes outbound calls to partner APIs. Key responsibilities:

  • Receive inbound requests from the gateway (sync) or Kafka consumer messages (async).
  • Determine the integration type and locate the partner profile from Config DB (Redis-cached, TTL 60 s).
  • Load the active mapping template version for the entity type and environment.
  • Invoke the Mapping Engine to produce a transformed, validated payload.
  • Select the appropriate outbound connector (REST, GraphQL, SOAP adapter, Kafka producer).
  • Execute the outbound call with circuit breaker and retry wrapper.
  • On success: persist external ID to integration_external_ids; publish success event; update run log.
  • On failure: classify error; apply retry policy; route to DLQ if exhausted; update run log with full diagnostic.

Engine Principle
The Mapping Engine is schema-agnostic. It operates on any JSON structure. CRM entity schemas are registered as JSON Schema fragments in the Config DB — not hardcoded. Adding a new CRM entity type requires only schema registration, not an engine code change.

Use Case A — CRM → ERP Customer Sync (SAP S/4HANA)

Business Context

When a new Account is created or updated in Arbormind CRM, the corresponding SAP Customer master record must be created or updated in S/4HANA within 30 seconds. SAP is the system of record for financial transactions; CRM is the system of record for relationship data. The integration is bi-directional: credit limit changes from SAP flow back into CRM as read-only fields.

Trigger

CRM emits a account.created or account.updated event to the Kafka topic crm.accounts.changed.

Flow

1

Event published

CRM API server publishes event with full account payload and idempotency key to Kafka topic.

2

Orchestrator consumes

Orchestration Service Kafka consumer picks up the message. Loads SAP partner profile and account→sap_customer mapping template (Redis-cached). Marks run log entry as IN_PROGRESS.

3

Mapping Engine executes

Five-phase pipeline transforms CRM account JSON → SAP KNA1 structure. External ID lookup checks if SAP customer already exists for this account. If found: PUT (update). If not found: POST (create).

4

SAP API call

REST Connector calls SAP OData endpoint with idempotency key in header. Retries on 5xx with exponential back-off. Circuit breaker monitored.

5

External ID stored

SAP Customer number (KUNNR) stored in integration_external_ids table. CRM account record updated with sap_customer_id field via internal CRM API.

Key Field Mappings

account.name→KNA1.NAME1truncate(35)mandatory
account.address.street→KNA1.STRAStruncate(35)mandatory
account.address.city→KNA1.ORT01directmandatory
account.address.postcode→KNA1.PSTLZdirectregex: postcode_gb
account.address.countryCode→KNA1.LAND1lookup(iso2_to_sap)enum: SAP country codes
account.vatNumber→KNA1.STCD1directformat: vat_gb (optional)
account.currency→KNA1.WAERSlookup(crm_to_iso4217)mandatory
account.status→KNA1.AUFSDif(active,"","01")enum: "",01,02
—→KNA1.KTOKDconst("0001")SAP account group

Use Case B — CRM → Billing Subscription Sync (Stripe)

Business Context

When a Contract in CRM moves to "Active" status, a corresponding Stripe Subscription must be created. Line items on the CRM contract map to Stripe Subscription Items. The Stripe Customer must already exist (created via Use Case A chain or standalone account sync). Stripe is the system of record for billing; CRM stores the Stripe subscription ID for reference.

Trigger

CRM emits contract.stage_changed event with newStage: "active". Orchestrator checks stage filter in partner event routing config before processing.

Flow

1

Stage change event

CRM publishes event. Routing config for Stripe partner filters on entity=contract AND newStage=active.

2

Dependency check

Orchestrator verifies Stripe Customer ID exists for the contract's account. If not found: triggers Account sync first (chained integration), waits up to 30 s for external ID to appear. If still missing: route to DLQ with reason DEPENDENCY_UNRESOLVED.

3

Payload construction

Mapping Engine builds Stripe Subscription create payload. Line items array-mapped: each CRM line item → Stripe Subscription Item with Stripe Price ID (resolved via external ID lookup) and quantity.

4

Stripe API call

POST /v1/subscriptions with Idempotency-Key header. On 409 (already exists): fetch existing subscription, compare, PATCH if delta found.

5

Write-back

Stripe subscription.id stored in CRM contract stripe_subscription_id field. Stripe customer portal link generated and stored.

Key Field Mappings

contract.account.externalId[stripe]→customerextId("stripe","account")mandatory
contract.lineItems[*].product.externalId[stripe]→items[*].priceextId("stripe","product")mandatory per item
contract.lineItems[*].quantity→items[*].quantitydirect (integer)min:1
contract.startDate→billing_cycle_anchortoEpoch()optional
contract.currency→currencylower()enum: ISO 4217 lowercase
contract.autoRenew→cancel_at_period_endnot(value)boolean
contract.id→metadata.crm_contract_idtoString()for reconciliation

Use Case C — CRM ← Identity Provider User Sync (Okta)

Business Context

When a new user is provisioned in Okta (or an existing user's profile is updated), a corresponding CRM Contact and User record must be created or updated in Arbormind. Okta is the system of record for user identity; CRM inherits display name, department, email, and job title. User deactivation in Okta must trigger CRM user deactivation within 60 seconds (security requirement).

Trigger

Okta sends a signed webhook event to the Integration Layer endpoint POST /v1/webhooks/idp/okta. The gateway verifies the X-Okta-Verification-Challenge HMAC signature before forwarding.

Flow

1

Webhook received

Gateway verifies HMAC-SHA256 signature. Responds 200 immediately (ack). Publishes verified payload to Kafka topic idp.users.changed for async processing.

2

Event classification

Orchestrator reads event type: user.lifecycle.create, user.profile.update, or user.lifecycle.deactivate. Routes to appropriate mapping template variant.

3

Deduplication check

For create events: check if CRM Contact with matching email already exists. If yes: switch to update path. If no: create path.

4

CRM record create/update

Mapping Engine transforms Okta user profile → CRM Contact + User payload. CRM API called to create or patch both records atomically.

5

Deactivation path

For deactivate events: CRM User isActive set to false; all active CRM sessions for that user revoked. Audit event written to CRM security log.

Key Field Mappings

profile.firstName→contact.firstNamedirectmandatory
profile.lastName→contact.lastNamedirectmandatory
profile.email→contact.email + user.emaildirectformat: email; mandatory
profile.department→contact.departmentdefault("Unknown")optional
profile.title→contact.jobTitledirectoptional
status→user.isActiveif(ACTIVE,true,false)boolean; mandatory
id→user.externalIddirectstored for reverse lookup

9.2 Assumptions

  • All partner systems expose documented REST or gRPC APIs. EDI-only partners (EDIFACT/X12) are deferred to v1.1 with a dedicated EDI adapter.
  • CRM records carry a stable, immutable UUID primary key that persists through the record lifecycle. This UUID is used as the correlation ID across all integration runs.
  • A Secrets Management infrastructure (HashiCorp Vault or AWS Secrets Manager) is deployed and operational before development Sprint 1 begins.
  • Partner sandbox environments are available and accessible from the DEV Kubernetes cluster within 2 weeks of project kick-off.
  • Each integration partner assigns a named technical contact reachable within 24 hours for schema clarification and sandbox access.
  • Kafka is available as a managed service (Confluent Cloud, AWS MSK, or Azure Event Hubs with Kafka protocol). Self-managed Kafka is not in scope.
  • The existing CRM PostgreSQL database (Neon DB) is available for the Config DB and Audit Log tables. A separate read replica is provisioned for Config DB queries under load.
  • Network connectivity between the Integration Layer Kubernetes cluster and all partner API endpoints is established and firewalled at the start of each environment build.

9.3 Constraints

  • Infrastructure boundary: All services must run within the existing Kubernetes cluster. No new cloud accounts without Infrastructure Board approval (minimum 4-week lead time).
  • Data residency: All personal data must remain within the EEA data boundary. US-based partner endpoints require SCCs countersigned before integration goes live.
  • Admin UI embedding: The Integration Layer admin UI must be embedded within the existing Arbormind CRM admin panel. No separate domain or standalone application.
  • No PCI data: The Integration Layer must never route, store, or log payment card numbers, CVVs, or PANs. Stripe's tokenisation must be used at source; only tokens transit the layer.
  • v1 Partner scope: General Availability (Q4 2026): ERP (SAP), Billing (Stripe), Identity (Okta) only. Additional partners in v1.1 (Q1 2027).
  • Team capacity: 3 backend engineers, 1 frontend engineer, 1 DevOps engineer allocated. Scope must be confirmed against this capacity by Sprint 2 planning.

CDC — Change Data CaptureA pattern where row-level changes to a database are streamed as events, typically via Debezium + Kafka. Used for near-real-time sync of partner master data.
Circuit BreakerA fault-tolerance pattern that stops outbound calls to a failing partner for a cooldown period, preventing resource exhaustion and cascading failures.
Config DBThe PostgreSQL database (hosted on Neon DB or equivalent) that stores partner profiles, mapping templates, lookup tables, and audit logs.
DLQ — Dead-Letter QueueA Kafka topic where messages are placed when all retry attempts have been exhausted. Entries are visible in the Ops Dashboard for manual intervention.
External IDThe identifier assigned to a CRM entity by a partner system (e.g. SAP Customer number). Stored in integration_external_ids and used to avoid duplicate creation.
Idempotency KeyA unique token sent with every mutating outbound request. Partners that honour it treat a duplicate request (same key) as a no-op, preventing double-writes on retry.
Mapping EngineThe shared TypeScript library that executes the five-phase transform pipeline (extract → enrich → transform → assemble → validate) against a loaded mapping template.
Mapping TemplateA versioned JSON document stored in Config DB that defines how a CRM entity maps to a partner entity, including field paths, transformation rules, and validation rules.
mTLS — Mutual TLSA TLS configuration where both the client and server present certificates for mutual authentication. Used for high-sensitivity connections.
Orchestration ServiceThe stateless Node.js microservice that coordinates the end-to-end integration flow: receiving events, loading config, invoking the Mapping Engine, calling partner connectors, and logging results.
Partner ProfileA Config DB record describing a partner system: name, base URL, auth method, rate limits, PII fields, and per-environment overrides.
SCIM — System for Cross-domain Identity ManagementA standard protocol (RFC 7643/7644) for user provisioning and deprovisioning between identity providers and service providers.
Transformation RuleA named, executable function applied to a source field value during the Transform phase of the Mapping Engine pipeline (e.g. concat, lookup, conditional).
Write-backAfter a successful outbound sync, writing the partner-assigned ID (external ID) back to the CRM entity record for future correlation.
